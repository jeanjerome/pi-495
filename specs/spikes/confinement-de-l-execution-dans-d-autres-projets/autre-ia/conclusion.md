# Ce que 495 reprend, adapte ou écarte

Cette section est une **recommandation de conception**, pas le relevé d'un comportement déjà présent dans 495. Elle s'appuie sur les fiches précédentes et sur les incidents fournis par le commanditaire. Aucun projet lu ne fournit, tel quel, l'ensemble des deux garanties demandées.

Source complémentaire lue pour préciser la recommandation Git : [G1] [documentation officielle `git-config`, section ENVIRONMENT](https://git-scm.com/docs/git-config#_environment), lue le 11 octobre 2026. Git n'est pas ajouté comme projet de confinement ; cette source définit les variables de configuration mentionnées ci-dessous.

## Besoin 1 — Des droits approuvés qui ne s'élargissent pas par le candidat

**Recommandation : un manifeste de contrôle approuvé, conservé hors de la copie candidate, puis compilé en une politique effective vérifiée avant chaque lancement.** Le candidat peut demander une évolution ; il ne peut ni modifier l'autorité qui l'accorde, ni changer la signification d'un chemin déjà accordé. Cette séparation reprend le plan de contrôle d'OpenShell et les restrictions administrées de Copilot. Elle écarte la fusion prioritaire du fichier projet de l'exemple Pi. [Fiches OpenShell, §1-2 ; Copilot local, §2 ; Pi, §2-3]

À la première exécution, présenter au propriétaire un relevé concret : commande, répertoire, lecture, écritures, temporaire, réseau, environnement, caches, services et exécuteur. Montrer aussi les droits ajoutés par le backend et les exceptions. Garder sa décision dans l'état de confiance de 495. Une modification de capacité demande une nouvelle décision. Reprendre la prévisualisation effective de Copilot et les traces d'Unsloth ; ne pas copier les ajouts automatiques de chemins personnels de Gemini. [Fiches Copilot local, §2-4 ; Unsloth, §2 ; Gemini, §2-4]

| Élément | Choix proposé pour 495 | Pourquoi et fondement |
|---|---|---|
| Autorité | Manifeste validé hors dépôt candidat ; modifications du candidat = propositions | Évite qu'un fichier projet élargisse les droits à la relance. Pi §2-3 ; OpenShell §1-2. |
| Racines écrites | Répertoires créés ou identifiés par le contrôleur ; refuser un lien qui change la portée | Une cible réelle peut être plus large que le nom approuvé. Codex §3 ; runtime Anthropic §2-3. |
| Ancêtres | Ne pas laisser le candidat remplacer les ancêtres des racines ou exceptions protégées | Le contrôle initial seul ne protège pas contre un renommage ultérieur. Codex §3 ; runtime Anthropic §3. |
| Temporaires | Un répertoire privé par exécution, extérieur aux données confidentielles | Réduit les effets croisés d'un `/tmp` globalement partagé. Unsloth §4. |
| Réseau | Conserver `denied`, `loopback`, `allowed`, mais montrer leur portée réelle | La possibilité d'atteindre un daemon local n'est pas une simple permission de fichier. Runtime Anthropic §6 ; Docker Sandboxes §6. |
| Caches | Cache dédié au contrôle, éventuellement initialisé depuis une source en lecture seule | Évite les credentials et l'empoisonnement des caches partagés. Copilot local §4 ; Unsloth §4. |
| Backend | Refus si indisponible ou si une règle requise n'est pas appliquée | Un démarrage dégradé ne répond pas au contrat. Unsloth §2-3 ; OpenShell §3 ; Pi §3. |

**Chemins et liens.** Pour `test-output -> .`, ne pas remplacer silencieusement le nom par sa cible et considérer l'autorisation acquise. Refuser cette racine d'écriture. Préparer le vrai répertoire de sortie hors de l'autorité du candidat, ou monter un volume contrôlé à cet emplacement. Vérifier chaque composant, les cibles existantes et les parents des créations. Conserver des identités/descripteurs stables lorsque le backend le permet ; sinon utiliser une copie préparée sans modification concurrente et des ancêtres non remplaçables. Si ces conditions ne sont pas réalisables, refuser cette politique. Ces dispositions adaptent le refus explicite de Codex, les montages d'ancêtres du runtime Anthropic et les ouvertures sans suivi de liens d'OpenShell ; elles demandent des tests propres à 495, pas une simple reprise de leur code. [Fiches Codex §3 ; runtime Anthropic §2-3 ; OpenShell §4 ; Gondolin §2]

**Git et environnement.** Garder la liste blanche, mais fournir un `HOME` et des répertoires XDG de contrôle. Construire une configuration Git de test indépendante de celle du propriétaire, avec identité et politique de signature explicites. Ne pas résoudre un besoin de signature en ouvrant `~/.ssh`. Si le contrôle vérifie réellement une signature, lui donner une clé de test dédiée et documentée. Traiter également la configuration du dépôt, ses hooks, les variables Git, `SSH_AUTH_SOCK` et les helpers de credentials comme des entrées de configuration. L'absence de clé lisible ne ferme pas un agent de signature. [Fiches Aider §4 ; Unsloth §4 ; Gemini §4 ; Docker Sandboxes §4]

Concrètement, le contrôleur peut imposer `GIT_CONFIG_GLOBAL` vers un fichier de test contrôlé et `GIT_CONFIG_NOSYSTEM=1`, ou fournir aussi un `GIT_CONFIG_SYSTEM` contrôlé. Ne pas hériter de `GIT_CONFIG_COUNT` et des paires `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>` : elles ajoutent des réglages prioritaires sur les fichiers. Git documente ces mécanismes. [G1] **Limite de cette proposition :** ces variables stabilisent le lancement ; elles n'empêchent pas un programme hostile de modifier son propre environnement. La confidentialité doit rester portée par les permissions OS et par l'absence des vrais credentials dans le worker.

**npm et Maven.** Ne pas autoriser globalement `~/.npm` ou `~/.m2` pour satisfaire une erreur de build. Commencer par des caches propres au contrôle et une configuration de registres explicite. Un cache réutilisé peut être initialisé depuis une source approuvée, puis disposer d'une couche d'écriture privée. Distinguer paquets, configuration des registres et credentials. La découverte automatique de Copilot montre pourquoi une permission de « cache » n'est pas nécessairement anodine. Aucun mécanisme universel Maven ne ressort des passages lus ; il reste à concevoir et qualifier pour 495. [Fiche Copilot local §4 ; limites relevées dans Unsloth, Gemini, Pi]

**Refus et proposition.** Enregistrer code de sortie, refus OS/proxy, chemin demandé et cible résolue, backend, politique et contexte. Distinguer un journal de confiance d'un message imprimé par le candidat. La sortie d'erreur peut aider à proposer un droit, jamais à l'accorder. Après accord, compiler une nouvelle politique et relancer ; ne pas transformer l'échec initial en succès. Reprendre le diagnostic de Gemini et du runtime Anthropic, avec l'autorité séparée de l'advisor OpenShell. [Fiches Gemini §2 ; runtime Anthropic §2 ; OpenShell §2]

**Chemins qui ne s'ouvrent jamais dans un contrôle ordinaire.** Conserver les exclusions fournies pour 495 (`~/.ssh`, `~/.aws`, `~/.gnupg`, authentification Pi). Y rattacher explicitement l'état de décision de 495, les politiques approuvées, les clés de preuve et les canaux de contrôle de l'exécuteur. Protéger aussi leurs alias et ancêtres ; fermer sockets d'authentification et daemon hôte par défaut. Le besoin exceptionnel se traite avec une ressource de test ou un autre exécuteur, pas en supprimant la protection de l'instance ordinaire. C'est une proposition pour 495, non une liste prétendument commune aux produits. [Contexte fourni ; fiches Codex §1-3 ; OpenShell §1-3 ; Docker Sandboxes §4-6]

## Besoin 2 — Juger ailleurs ce qui ne peut pas tourner confiné, sur la même révision

**Recommandation : deux voies d'exécution, une seule identité de candidat et une seule décision de vérification.** Les contrôles ordinaires utilisent Seatbelt/bubblewrap qualifiés. Les contrôles qui démarrent eux-mêmes un sandbox, ou ont besoin de Docker, sont affectés explicitement à un exécuteur extérieur. Celui-ci reçoit la même révision et le même contrat de contrôle. Il ne s'agit pas d'une relance automatique du shell sur le poste. [Fiches Codex §5-6 ; Cursor cloud §6 ; Docker Sandboxes §6 ; limites de Claude Code §2 et Pi §3]

| Contrôle | Exécuteur proposé | Condition à qualifier |
|---|---|---|
| Test, lint, couverture, mutation ordinaires | Backend local 495 qualifié | Droits effectifs, environnement et refus attendus. |
| Tests qui lancent `sandbox-exec` | Worker macOS dédié ou VM macOS qualifiée, sans profil Seatbelt extérieur incompatible | Appliquer réellement les profils du candidat ; protéger le poste par la frontière extérieure, pas par un second profil supposé compatible. |
| Tests qui lancent bubblewrap | Worker Linux dédié, idéalement dans une VM | Capacités noyau, namespaces et restrictions de l'environnement extérieur effectivement compatibles. |
| Testcontainers / Docker | VM Linux dédiée avec daemon Docker privé | Aucun socket du daemon hôte ; services, réseau et ressources intérieurs à la VM. |

Le choix macOS découle de l'incident fourni et du saut explicite des tests Seatbelt chez Codex ; **aucune recette de VM macOS n'a été essayée ni validée dans cette étude**. La voie Linux/Docker reprend l'architecture concrète de Docker Sandboxes ; Cursor documente aussi Docker dans son environnement distant. La compatibilité bubblewrap doit être sondée sur l'exécuteur, et non déduite de la présence du binaire. [Fiches Codex §5 ; Copilot local §5 ; Docker Sandboxes §5-6 ; Cursor cloud §5-6]

Pour rendre « même révision » vérifiable, l'exécuteur doit recevoir un instantané identifié : commit et empreinte de l'arbre effectivement testé. Décider explicitement si des fichiers non suivis sont exclus ou inclus dans un paquet dont l'empreinte est enregistrée. Ne pas juger une branche mobile par son seul nom. Associer au résultat : révision, manifeste du contrôle, empreinte de politique, image/exécuteur, versions du backend, résultats de qualification, sortie, erreurs et tests sautés. Le contrôleur de confiance vérifie cette correspondance avant de compter la preuve. C'est une exigence proposée pour 495 ; les produits distants lus ne prouvent pas automatiquement ce contrat pour lui. [Fiches OpenHands §1-2 ; SWE-agent/SWE-ReX §1-2 ; Copilot cloud §1-2 ; Unsloth §2]

Le service extérieur ne doit pas exposer une commande générique « exécuter hors sandbox sur l'hôte ». Il doit créer ou sélectionner un worker isolé, y transmettre l'instantané, exécuter le contrôle approuvé, récupérer les résultats et réinitialiser l'état approprié. Ses credentials d'administration, sockets et politiques restent hors de la charge candidate. Même un conteneur disposant du daemon Docker hôte ne satisfait pas ce contrat. [Fiches OpenShell §1 ; Docker Sandboxes §1-6 ; OpenHands §6 ; SWE-agent/SWE-ReX §6]

**Qualification et statut des tests.** Séparer les tests purs de génération de politique des essais effectifs du backend. Pour ces derniers, vérifier d'abord les témoins hors confinement, puis les accès permis et refusés, avec inspection extérieure des effets. Couvrir le lien vers `.`, le lien vers un parent, le lien cassé, le remplacement après vérification, les chemins absents, la configuration Git globale, l'agent SSH et les caches. Un test sauté parce qu'il est déjà sous Seatbelt est **non exécuté**, jamais « validé ». Le contrôle obligatoire demeure incomplet tant que son exécution sur le worker approprié n'a pas produit la preuve attendue. [Fiches Unsloth §5 ; Codex §5 ; runtime Anthropic §2-5 ; Gondolin §2-5 ; Docker Sandboxes §4]

**Choix écartés.** Pas d'élargissement déclenché par un lien ou un fichier du candidat ; pas de conversion d'un refus en autorisation ; pas de repli non confiné en cas de backend indisponible ; pas d'affaiblissement silencieux du confinement pour faire passer un test imbriqué ; pas d'acceptation globale lorsque les contrôles incompatibles ont seulement été sautés. Ces exclusions sont les conséquences des deux besoins, éclairées par les mécanismes et limites relevés chez Pi, Gemini, Codex, le runtime Anthropic et OpenShell. [Fiches correspondantes, §2-6]
