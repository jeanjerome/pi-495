2. **Droits.** *Déclaration.* Le mode `workspace-write` lit tout le disque. Il écrit dans les racines du projet, dans `/tmp` et dans `$TMPDIR`, sauf si `exclude_slash_tmp` ou `exclude_tmpdir_env_var` sont posés, et dans les `writable_roots` ajoutées (`protocol/src/permissions.rs:819-858` ; [S5]). Le réseau est coupé par défaut ; `sandbox_workspace_write.network_access = true` l'ouvre [S3]. Les profils nommés `[permissions.<nom>]` accordent `read`, `write` ou `deny` par chemin, par jeton (`:workspace_roots`, `:minimal`, `:tmpdir`) ou par glob de lecture interdite comme `"**/*.env" = "deny"`. Le plus spécifique gagne ; à spécificité égale, `deny` l'emporte sur `write`, et `write` sur `read` [S4]. *Découverte d'un droit manquant.* Codex n'a pas de journal fiable des refus en exécution normale. Il devine : un code de sortie non nul, hors 2, 126 et 127, accompagné d'un mot-clé comme « operation not permitted », « permission denied », « read-only file system » ou « sandbox ». Sous Linux, s'y ajoute une mort par SIGSYS. Le commentaire du code l'admet : « We don't have a fully deterministic way to tell if our command failed because of the sandbox » (`sandboxing/src/denial.rs:5-72`). Pour le diagnostic, `codex sandbox macos --log-denials -- <cmd>` lance la commande sous le profil. Pendant ce temps, il lit `log stream` avec le prédicat `subsystem == "com.apple.sandbox.reporting"`, garde les lignes `Sandbox: nom(pid) deny(...) capacité` des PID de l'arbre de processus, et les affiche à la sortie (`cli/src/debug_sandbox/seatbelt.rs:87-113` ; `cli/src/lib.rs:89-91`). C'est un mode d'apprentissage manuel, pas branché sur l'agent. *Octroi.* L'outil shell accepte `sandbox_permissions` : `with_additional_permissions` pour élargir le bac à sable pour une commande, ou `require_escalated` pour une exécution hors bac à sable. Il prend aussi une `justification` (la question montrée à l'utilisateur) et un `prefix_rule` (`core/src/tools/handlers/shell_spec.rs:239-263`). La consigne donnée au modèle dit : si une commande importante échoue « because of sandboxing », la relancer avec `require_escalated` (`prompts/templates/permissions/approval_policy/on_request.md:26-32`). Une règle de préfixe approuvée peut être gardée d'une session à l'autre dans `$CODEX_HOME/rules/default.rules` (`core/src/exec_policy.rs:54-56,868`). L'orchestrateur ne relance lui-même une commande refusée hors bac à sable, après approbation, qu'avec la politique interne `untrusted` ou avec `granular.sandbox_approval = true`. Avec `on-request` ou `never`, il rend le refus au modèle (`core/src/tools/sandboxing.rs:345-351` ; `core/src/tools/orchestrator.rs:439-470,517-560`). `on-failure` n'est plus qu'un alias de `on-request` (`protocol/src/protocol.rs:1099-1102`) ; [S5] le dit déprécié. *Qui accorde.* L'utilisateur par défaut. `approvals_reviewer = auto_review` confie les demandes éligibles à un agent relecteur [S2].
