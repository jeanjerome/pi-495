### GitHub Copilot (Copilot CLI, VS Code, agent cloud)

Signée : Claude (Opus 5.5), le 11 octobre 2026.

Copilot confine les commandes de l'agent par trois chemins distincts : (a) le Copilot CLI et les sessions « Agent Host » de VS Code, qui partagent le moteur du SDK Copilot, lui-même adossé à MXC (Microsoft eXecution Container) ; (b) l'ancien harnais « Local » de VS Code, qui enveloppe la commande dans `@vscode/sandbox-runtime` ; (c) l'agent cloud, qui tourne dans un runner GitHub Actions éphémère derrière un pare-feu. La fiche les distingue partout où ils diffèrent.

1. **Ce qui est confiné.**
   - CLI et Agent Host : les commandes shell, les recherches intégrées (`grep`/`glob` lancent ripgrep confiné) et, par défaut, les serveurs MCP et LSP locaux tournent sous le bac à sable du système. Les outils intégrés de lecture et d'écriture de fichiers tournent dans le processus du CLI, qui n'est pas confiné : ils vérifient la même politique « en logiciel », sans appui du noyau. Les serveurs MCP distants ne sont pas confinés. Les sous-agents suivent l'outil qu'ils appellent [S2 l.15-23] [S1 l.50]. Le bac à sable est désactivé par défaut [S1 l.28] ; VS Code idem (`chat.agent.sandbox.enabled` = `off`) [S10 l.79] [S11 `terminalChatAgentToolsConfiguration.ts:541`].
   - Moteur : MXC applique la politique déclarée par le CLI — Seatbelt sous macOS, bubblewrap sous Linux, ProcessContainer sous Windows [S1 l.32-34, 79-87] [S13 `README.md`]. Seatbelt est appliqué par `sandbox_init()` entre `fork()` et `exec()`, pas par `sandbox-exec` [S13 `seatbelt-backend.md:20`, `seatbelt_runner.rs:7`]. Ce n'est « ni une machine virtuelle ni une frontière de compte » [S10 l.36].
   - Harnais Local de VS Code : la commande est réécrite en `"<node>" "<…>/@vscode/sandbox-runtime/dist/cli.js" --settings <json> -c '<commande>'` [S11 `terminalSandboxEngine.ts:271`] ; pas de Windows [S11 `settings.ts:28-30`].
   - Agent cloud : tout tourne dans un runner Actions éphémère (Ubuntu x64 ou Windows 64 bits) [S8 l.7, 155]. Le pare-feu ne s'applique qu'aux processus lancés par l'outil Bash de l'agent, pas aux serveurs MCP ni aux étapes `copilot-setup-steps` [S7 l.27].

2. **Droits.**
   - Déclaration : `~/.copilot/settings.json`, clé `sandbox` (`userPolicy.filesystem.readwritePaths|readonlyPaths|deniedPaths`, `network.allowOutbound|allowLocalNetwork|allowedHosts|blockedHosts`, `allowBypass`, `allowDevToolAccess`, `auth.git|gh`) [S4 l.314] [S11 `sandboxConfigForSdk.ts:14-101`]. **« Sandbox settings are not supported in repository-level settings files »** [S4 l.314] : un dépôt ne peut pas élargir le bac à sable du CLI. Précédence `denied` > `readonly` > `readwrite`, et le chemin le plus spécifique l'emporte [S2 l.71-77] [S11 `sandboxConfigForSdk.ts:108-150`].
   - Droits automatiques : lecture-écriture du répertoire courant ; dans un dépôt git, lecture de tout le dépôt et écriture de `.git` [S4 l.196-199] ; lecture seule des répertoires de `PATH` et de variables d'outillage (`JAVA_HOME`, `GOPATH`, `GIT_CONFIG_SYSTEM`…), sauf racines et répertoires système [S5 §Sandbox tool directory grants] ; caches de gestionnaires de paquets, la plupart en lecture, certains en écriture (cache npm, caches de build) [S2 l.57-63].
   - Découverte : `/sandbox policy` affiche la politique effective du répertoire courant ; `/sandbox policy <commande>` montre ce qu'une commande recevrait **sans l'exécuter ni créer de répertoire** [S2 l.79-103]. Après un refus : un échec dont le diagnostic EPERM/EACCES nomme un chemin bloqué propose une ré-exécution hors bac à sable [S12 `changelog.md:274-275`] ; sous Windows seulement, un « learning mode » enregistre les accès refusés (`deny`, par défaut) ou les enregistre et les permet (`allow`) [S6 §`sandbox.learningMode`] [S13 `logging-access-denied.md:1-20`]. Le harnais Local de VS Code, lui, reconnaît un refus par expression régulière sur la sortie (`Operation not permitted|Permission denied|Read-only file system|…|No such file or directory`) et injecte au modèle la consigne d'élargir `allowWrite` avec l'utilisateur ou de redemander hors bac à sable [S11 `sandboxOutputAnalyzer.ts:49-61, 81-84`].
   - Octroi : l'utilisateur, par `/sandbox config` ou le fichier ; une invite approuve une ré-exécution hors bac à sable (une commande, ou toute la session) [S3 l.88-96]. Les réglages gérés d'entreprise (serveur, MDM, fichier) se combinent dans le sens le plus restrictif : un chemin accordé par l'utilisateur ne survit que s'il figure mot pour mot dans chaque liste gérée [S6 §`sandbox.userPolicy.filesystem`] [S2 l.123-127].
   - Harnais Local de VS Code : droits de lecture accordés **selon le mot-clé de la commande** analysé par tree-sitter (`git` ouvre `~/.gitconfig`, `npm` ouvre `~/.npm`, `mvn` ouvre `~/.m2/repository`…) [S11 `terminalSandboxReadAllowList.ts:27-79, 96-238`, `commandLineSandboxRewriter.ts:44-56`]. Les réglages sont `restricted: true`, donc non lus depuis les réglages d'un espace de travail non approuvé [S11 `configurationRegistry.ts:229-233`] ; la source ne dit pas qu'ils sont refusés depuis un espace approuvé.

3. **Refusé quoi qu'on déclare.**
   - Le CLI refuse `/sandbox enable` sur un hôte non pris en charge et, si l'entreprise exige `failIfUnavailable`, bloque modèle et outils plutôt que de tourner sans bac à sable [S1 l.100-104] [S6]. Une politique illisible fait basculer au plus restrictif [S5 §Enterprise-managed sandbox floor]. Un chemin refusé que Windows ne sait pas garantir fait échouer la commande plutôt que de l'exécuter affaiblie [S4 l.65, 232].
   - MXC/Seatbelt : rejette tout chemin contenant `..` (sinon un refus pourrait « échouer ouvert ») et tout filtrage réseau par hôte ou CIDR, que Seatbelt ne sait pas exprimer [S13 `seatbelt-backend.md:64-86, 624-633`] ; SIP prime sur le profil [S13 l.183-184].
   - La source ne donne aucune liste de chemins sensibles jamais ouverts côté CLI : le défaut est « deny-by-default » et le répertoire personnel n'est pas accordé [S2 l.25-33] [S3 l.20], mais « Allow dev tool access » ouvre des fichiers de configuration contenant des jetons de registre [S4 l.204].
   - Harnais Local : le répertoire personnel entier est en `denyRead`, le fichier de politique aussi [S11 `terminalSandboxEngine.ts:654, 867-874`] ; en revanche toute commande `git` rouvre `~/.ssh` en lecture et `~/.gnupg` en lecture-écriture avec `allowAllUnixSockets` — sauf si une commande `docker*` figure dans l'invocation, parce que « Docker socket access can grant host-level privileges » [S11 `terminalSandboxReadAllowList.ts:361-374`, `terminalSandboxRuntimeConfigurationPerOperation.ts:36-47, 86-91`].

4. **Environnement de l'hôte.**
   - MXC part toujours d'un environnement vide (`--clearenv` sous bwrap, environnement effacé sous Seatbelt), avec un bloc `PATH`/`TERM` et `HOME` = répertoire de travail ; la doc avertit que les fichiers `.gitconfig`, `.npmrc`, `.config/*` du répertoire de travail sont alors lus **comme configuration utilisateur**, et recommande de passer un autre `HOME` quand l'espace n'est pas de confiance [S13 `seatbelt-backend.md:393-430`, `bubblewrap-backend.md:212-237`]. Sous bwrap, `$HOME`, `/opt`, `/var`, `/run/user/<uid>` sont invisibles par défaut [S13 `bubblewrap-backend.md:131-145`].
   - Ce que le CLI passe ensuite à MXC est non lu (binaire fermé). La doc et le journal disent : le `GITHUB_TOKEN` ambiant est retenu [S12 `changelog.md:48`] ; git et `gh` reçoivent des identifiants factices, qu'un proxy local remplace par les vrais pour les seules destinations HTTPS approuvées ; d'autres variables peuvent être masquées de même (`sandbox.credentials.envVars`) [S3 l.24-28] [S4 l.140-190] ; `--secret-env-vars` retire des variables [S5 l.720] ; trousseau macOS fermé par défaut [S4 l.148]. Sur `~/.gitconfig` (signature, `url.insteadOf`), la source ne le dit pas ; le journal mentionne des « SSH remote rewrites » pour git confiné [S12 `changelog.md:63`].
   - Caches : `~/.npm`, caches de build et `uv` sont inscriptibles avec « dev tool access », et la doc prévient qu'ils sont partagés avec les commandes non confinées [S2 l.57-61] [S12 `changelog.md:55`].
   - Harnais Local : le code de VS Code n'efface aucune variable — il préfixe seulement `PATH`, `TMPDIR`, `CLAUDE_TMPDIR` [S11 `terminalSandboxEngine.ts:271`] ; ce que fait ensuite sandbox-runtime est non lu ici.
   - Agent cloud : seules les variables et secrets de type « Agents » sont exposés, comme variables d'environnement ; ceux préfixés `COPILOT_MCP_` vont aux seuls serveurs MCP [S9 secrets l.18, 61-66].

5. **Tester sous confinement.**
   - Aucune source lue ne décrit l'emboîtement de Seatbelt ni une variable qui signalerait au code confiné qu'il l'est. MXC/Seatbelt n'a aucun traitement de l'emboîtement (recherche sans résultat dans `src/mxc-sdk/src/backends/seatbelt/`) [S13].
   - Linux, harnais Local : VS Code sonde `bwrap --unshare-net --dev-bind / / echo ok` ; si bwrap est installé mais inutilisable et qu'AppArmor n'en est pas la cause, il **active de lui-même** `enableWeakerNestedSandbox` et continue [S11 `sandboxHelper.ts:251-262`, `terminalSandboxEngine.ts:312-323`]. Ce mode monte `/proc` de l'hôte au lieu d'un `/proc` neuf [S15 `linux-sandbox-utils.ts:3551-3560`] et « considerably weakens security » [S15 `README.md:1050`].
   - Dev Container : pour qu'un bac à sable tourne dans le conteneur, VS Code réécrit la configuration avec `seccomp=unconfined`, `apparmor=unconfined`, `systempaths=unconfined` et `/dev/net/tun`, puis vérifie par `docker inspect` que le conteneur réel les porte [S11 `devContainerSandbox.ts:13-14, 92-141, 143-174`].
   - Tests de MXC : « There is no skip path — a missing prerequisite fails, so a green run always means the assertions executed » [S13 `seatbelt-backend.md:679-684`].

6. **Frontière pour un bac à sable ou Docker.**
   - Local : aucune frontière dédiée. MXC prévient qu'un `readwritePaths` large donne `connect()` sur tout socket Unix existant dessous, et qu'un socket Docker, `ssh-agent` ou `gpg-agent` est « un plan de contrôle » à mettre en `deniedPaths` [S13 `seatbelt-backend.md:133-153`]. Le réseau local est fermé par défaut dans le CLI ; sous macOS cela bloque même un serveur que la commande démarre sur 127.0.0.1 [S12 `changelog.md:354`] [S4 l.245-251].
   - Le bac à sable ne remplace ni les sessions cloud ni les Dev Containers [S10 l.38].
   - Agent cloud : la frontière est le runner Actions éphémère ; `copilot-setup-steps.yml` accepte `services` (conteneurs de service), hors pare-feu [S8 l.70-79] [S7 l.27]. Les workflows CI d'une PR de l'agent ne tournent qu'après le clic « Approve and run workflows » d'un humain ayant l'écriture [S9 risks l.28]. Runners auto-hébergés : pare-feu à désactiver, réseau à cloisonner soi-même [S8 l.159-182].
   - « Cloud sandboxing » du CLI (`copilot --cloud`) : session entière dans un environnement Linux éphémère sur Azure Container Apps Sandboxes [S1 l.112-137].

7. **Coût.**
   - Plateformes : macOS 15+ (Seatbelt) ; Linux avec bwrap ≥ 0.5.0, et pour le réseau `slirp4netns`, `unshare`/`nsenter` (util-linux ≥ 2.35), `iptables`, `/dev/net/tun` ; Windows 11 avec la mise à jour de septembre 2026 [S1 l.79-87]. Harnais Local : bwrap + socat, pas de Windows [S10 l.49-53] [S11 `sandboxHelper.ts:194-213`].
   - Temps de démarrage : la source ne le dit pas. Une sonde bwrap a un délai de 5 s [S13 `bubblewrap-backend.md:38-50`].
   - Entretien : le journal du CLI compte 110 lignes mentionnant « sandbox » entre la 1.0.57 (2026-06-01) et la 1.0.95 (2026-10-09), dont des cas d'outils un par un (pnpm, uv, Bazel, Gradle, sockets Unix de jest/vite) [S12 `changelog.md:55-56, 362, 397, 450`].
   - Prix : bac à sable local inclus ; bac à sable cloud facturé à la seconde de calcul et de mémoire [S1 l.171-181] ; session d'agent cloud limitée à 59 minutes [S8 l.77].

- *Reprendre (besoin 1).* La source dit : les réglages du bac à sable ne sont pas lus depuis le dépôt, et les sources gérées ne peuvent que restreindre [S4 l.314] [S6]. J'en déduis le patron pour 495 : les droits d'un contrôle vivent hors de la copie candidate, et toute source nouvelle ne peut que les rétrécir. C'est l'inverse de Cursor, qui fusionne un `sandbox.json` du dépôt avec priorité.
- *Reprendre (besoin 1).* La source dit : `/sandbox policy <commande>` montre les droits qu'une commande recevrait sans l'exécuter [S2 l.89-95]. J'en déduis la forme de la proposition faite au propriétaire à la première exécution : la politique effective, rendue lisible, avant tout lancement. Le « learning mode » deny-and-record [S6] est le seul mécanisme lu qui enregistre les refus sans affaiblir le confinement, mais il est Windows seulement. Sous macOS et Linux, Copilot n'a qu'une heuristique sur EPERM/EACCES [S12 l.274].
- *Adapter (liens).* La source dit : un lien dans un répertoire autorisé n'accorde pas sa cible, et les droits gardent leur graphie [S2 l.113] [S5]. MXC ne résout que les racines système liées (`/tmp` → `/private/tmp`) et rejette `..` [S13 l.114-131, 624-633]. J'en déduis, sans l'avoir essayé, que le lien `test-output -> .` n'aurait pas élargi un droit accordé sur `test-output` : le noyau aurait résolu l'écriture vers la copie, que la règle ne couvre pas, et l'aurait refusée.
- *Écarter.* Le harnais Local de VS Code fait deux choses contraires à 495. Il passe de lui-même en bwrap affaibli quand la sonde échoue [S11 l.312-323], là où 495 refuse avec `capability_missing`. Il rouvre aussi `~/.ssh`, `~/.gnupg` en écriture et tous les sockets Unix pour toute commande `git` [S11]. 495 ferme justement ces chemins et veut tenir la configuration git de l'hôte à l'écart. L'avertissement de MXC est plus utile : un `HOME` pointé vers un répertoire privé évite de lire le `.gitconfig` de l'hôte, ou celui du candidat comme configuration utilisateur [S13].
- *Besoin 2.* Aucune source ne fait tourner un bac à sable ou Docker sous le bac à sable local. VS Code déconfine le Dev Container pour y loger bwrap [S11 `devContainerSandbox.ts`], et GitHub renvoie ces cas à une machine éphémère : runner Actions, `services`, sandbox cloud [S8] [S1]. La CI d'une PR d'agent attend une approbation humaine et tourne ensuite sur la révision poussée [S9]. C'est le patron « jugé ailleurs, sur la même révision » que cherche 495.
