1. **Ce qui est confiné.** Le *builder* d'une dérivation et tous ses descendants ; rien d'autre (pas d'évaluation, pas de démon). Le mode se choisit par le réglage `sandbox` : `true`, `false` ou `relaxed`, vrai par défaut sous Linux et FreeBSD, faux ailleurs, macOS compris (`local-settings.hh:361-395`). Constructeurs : chroot + espaces de noms sous Linux, chroot sous FreeBSD, Seatbelt sous macOS (`unix-derivation-builder.cc:1121-1138`).
   - *macOS.* Nix compose un profil SBPL et l'applique dans l'enfant par `sandbox_init_with_parameters`, pas par `sandbox-exec` (`darwin-derivation-builder.cc:174-179`). Profil complet : `(deny default)` (`:78-84`, `sandbox-defaults.sb:5`), puis lecture-écriture-exécution sur les sorties (`:96-100`), sur les entrées du magasin et les chemins autorisés (`:104-135`), lecture des ancêtres de chaque chemin pour `realpath()` (`:137-142`), écriture dans `/tmp`, le `TMPDIR` global et le dossier de construction (`sandbox-defaults.sb:36-39`), signaux limités au même bac (`:27`), périphériques standards (`:74-83`). **Même sans bac à sable, macOS applique `sandbox-minimal.sb`** : `(allow default)` moins la création de binaires setuid/setgid (`sandbox-minimal.sb:3-7`, `darwin-derivation-builder.cc:145-148`).
   - *Linux.* Espaces de noms PID, montage, IPC, UTS, utilisateur s'il est disponible, et réseau sauf pour une sortie fixe (`linux-derivation-builder.cc:518-583`). La racine est un chroot qui ne contient que les entrées du magasin, `sandbox-paths`, le dossier de construction, un `/dev` minimal, un `/proc` neuf (`chroot-derivation-builder.cc:32-71`, `linux-derivation-builder.cc:752-848`). Un `/etc/passwd` et un `/etc/group` de trois lignes sont écrits (`:650-664`). S'y ajoutent seccomp (`:116-177`), `PR_SET_NO_NEW_PRIVS` (`:405-410`) et, pour les noyaux récents, Landlock limité aux sockets Unix abstraites (`:201-241`).
   - *Utilisateurs de construction.* Sous démon, chaque construction tourne sous un compte du groupe `build-users-group`, jamais deux à la fois sous le même compte (`local-settings.hh:286-319`). Sous Darwin, les objets IPC SysV de ce compte sont détruits après la construction, faute d'espace de noms IPC (`darwin-derivation-builder.cc:209-311`).

2. **Droits.** Deux auteurs, deux niveaux.
   - *La configuration du démon* (`nix.conf`, écrite par l'administrateur) : `sandbox`, `sandbox-paths` / `extra-sandbox-paths` (montages `cible=source`, `?` pour un chemin facultatif, `local-settings.hh:397-416`), `allowed-impure-host-deps` (`:483-487`), `system-features` (`globals.hh:312-354`), `pre-build-hook`, qui peut ajouter des chemins par dérivation (`unix-derivation-builder.cc:447-474`), `filter-syscalls`, `allow-new-privileges` (`local-settings.hh:579-604`). Un client du démon ne peut changer ces réglages que s'il est dans `trusted-users` ; sinon le démon ignore le réglage avec un avertissement (« restricted setting and you are not a trusted user », `daemon.cc:297-309`). Le manuel tient `trusted-users` pour « essentiellement équivalent » à un accès root (`src/nix/unix/daemon.cc:60-75`).
   - *La dérivation* (écrite par l'auteur du paquet) demande, et la configuration borne :
     - `__noChroot` : refusé quand `sandbox = true`, respecté en `relaxed` (`unix-derivation-builder.cc:1067-1085`) ;
     - `__sandboxProfile` (texte SBPL ajouté tel quel à la fin du profil, `darwin-derivation-builder.cc:144`) : refusé quand `sandbox = true`, accepté en `relaxed` (`unix-derivation-builder.cc:1073-1079`). Le test `extra-sandbox-profile.sh:23-25` vérifie ce refus avec un profil `(allow file*)` ;
     - `__impureHostDeps` : chaque chemin doit tomber sous un préfixe de `allowed-impure-host-deps`, sinon erreur (`unix-derivation-builder.cc:416-443`). Défaut macOS : `/System/Library`, `/usr/lib`, `/dev`, `/bin/sh` ; vide ailleurs (`globals.cc:95-108`). Le commentaire de `unix-derivation-builder-impl.hh:165` dit « si le bac est en mode relaxed », mais le code lu ne teste pas le mode ;
     - `__darwinAllowLocalNetworking` : **aucun garde-fou de configuration**. La dérivation l'obtient seule, même en `sandbox = true` ; il passe en paramètre `_ALLOW_LOCAL_NETWORKING` (`darwin-derivation-builder.cc:169-172`, `sandbox-defaults.sb:51-71`) ;
     - devenir une sortie fixe (`outputHash`) : la dérivation obtient alors le réseau (point 6), contre un hachage vérifié et zéro référence au magasin (`derivation-check.cc:21-40`).

     Réponse à la question posée : oui, une dérivation peut élargir ses propres droits, mais seulement dans l'enveloppe que l'administrateur a ouverte (mode `relaxed`, préfixes autorisés) — sauf le réseau local sous macOS et le réseau d'une sortie fixe, que la dérivation s'accorde elle-même.
   - *Découverte d'un droit manquant.* Les refus de configuration sont explicites et nomment le réglage : « requested impure path '…', but it was not in allowed-impure-host-deps » (`unix-derivation-builder.cc:437`), « has '__noChroot' set, but that's not allowed when 'sandbox' is 'true' » (`:1069-1072`). Les refus du noyau, eux, sont muets : sous macOS, le profil porte `(deny default (with no-log))` sauf si `darwin-log-sandbox-violations = true`, et le refus part alors dans le journal système, sans destination configurable (`darwin-derivation-builder.cc:78-84`, `local-settings.hh:489-494`). Il n'y a pas de mode « apprentissage ». S7 montre le coût : un `EPERM` de Seatbelt fait planter Nix lancé dans une construction (« getting status of /nix/var/nix/profiles/per-user/root/channels/nixpkgs: Operation not permitted »).

3. **Refusé quoi qu'on déclare** (du côté de la dérivation ; l'administrateur peut lever certains de ces refus) :
   - la création de binaires setuid/setgid : seccomp sous Linux (`linux-derivation-builder.cc:116-152`), `(deny file-write-setugid)` sous macOS, y compris dans le profil minimal (`sandbox-defaults.sb:9`, `sandbox-minimal.sb:7`). L'administrateur peut couper seccomp (`filter-syscalls`) ;
   - les attributs étendus et les ACL : `ENOTSUP` (`linux-derivation-builder.cc:158-167`) ;
   - l'acquisition de privilèges par setuid ou capacités de fichier, sauf `allow-new-privileges` (`local-settings.hh:590-604`) ;
   - un chemin de montage qui sort du chroot par `..`, ou qui retombe sur la racine du chroot (`linux-derivation-builder.cc:317-319`, `:367-369`) ;
   - sous macOS, une correspondance `cible=source` différente (« mismatched impure paths not supported on Darwin », `darwin-derivation-builder.cc:117-121`) ;
   - `uid-range` hors bac à sable (`unix-derivation-builder.cc:1118-1119`) ; un `sandbox-build-dir` qui contient le magasin (`:411-413`) ;
   - pour un client non approuvé : la construction d'une dérivation adressée par ses entrées envoyée directement (`daemon.cc:678-679`), la réparation, les substituts non approuvés.

   *Liens symboliques.* Le montage Linux ouvre chaque composant avec `O_NOFOLLOW`. Il ouvre la source en `O_PATH | O_NOFOLLOW`. Il recrée un lien source comme un lien, sans le suivre (`linux-derivation-builder.cc:327-328`, `:353`, `:372-385`). En revanche, la vérification de `__impureHostDeps` contre les préfixes autorisés est lexicale, sans résolution des liens, « pour ne pas renseigner un non-root sur des fichiers inaccessibles » (`unix-derivation-builder.cc:422-424`). Quelques chemins système (`/etc/resolv.conf`…) sont, eux, résolus « pour compatibilité » (`:804-809`). Sous macOS, Seatbelt reçoit `subpath` pour un dossier et `literal` pour un fichier, choisi par `lstat` (`darwin-derivation-builder.cc:124-133`) ; ce que Seatbelt fait d'un lien, la source ne le dit pas.

4. **Environnement de l'hôte.** L'environnement est vidé (`env.clear()`), puis rempli des seuls attributs de la dérivation (`unix-derivation-builder.cc:579-670`, manuel `store/building.md:143-171`). `PATH=/path-not-set`, pour qu'aucun shell ne prenne son défaut. `HOME=/homeless-shelter`, chemin inexistant : un outil qui lit `HOME` ne trouve aucune configuration, et n'a pas de raison de consulter `/etc/passwd`. Sans bac à sable, Nix refuse de construire si `/homeless-shelter` existe (`:344-347`). `TMPDIR`, `TEMPDIR`, `TMP`, `TEMP` pointent sur le dossier de construction ; `TERM`, `NIX_STORE`, `NIX_BUILD_CORES`, `NIX_LOG_FD` sont fixés. Seule une sortie fixe reçoit des variables de l'appelant (`impureEnvVars`, proxys par exemple), et ce sont celles **du démon**, pas du client (`:648-661`, manuel `store/derivation/index.md:200-211`). Sous Linux, `/etc/nsswitch.conf` est réécrit pour une sortie fixe (« hosts: files dns »), afin de limiter les impuretés (`linux-derivation-builder.cc:783-801`).
   Pour sa propre suite de tests, Nix isole git explicitement : `GIT_CONFIG_SYSTEM=/dev/null`, `GIT_CONFIG_GLOBAL=/dev/null`, avec le commentaire « Isolate tests from host git config (signing, url rewrites, etc.) ». Il désarme aussi `XDG_*` et `GIT_DIR`, et pose `HOME` sur un dossier de test (`tests/functional/common/vars.sh:60-69`).
   *Caches.* Une construction ne voit aucun cache de l'utilisateur : seulement les chemins du magasin de sa clôture. Une dépendance téléchargée passe par une sortie fixe au hachage déclaré (point 6). Comment nixpkgs en tire un cache npm ou Maven : non lu.

5. **Tester sous confinement.**
   - *macOS : Nix n'emboîte pas Seatbelt, il l'éteint.* `test-main.cc:37-42` : « Avoid this error, when already running in a sandbox: sandbox-exec: sandbox_apply: Operation not permitted ». Les tests unitaires posent alors `sandbox = false` **et** `_NIX_TEST_NO_SANDBOX=1`. Cette variable saute jusqu'au profil minimal, qui serait lui aussi refusé (`darwin-derivation-builder.cc:163`). Les tests fonctionnels font de même quand `NIX_STORE` est défini, c'est-à-dire quand ils tournent dans une construction Nix (`tests/functional/common/vars.sh:47-49`). La CI macOS construit justement ces tests comme dérivations, avec `sandbox = true` (`.github/workflows/ci.yml:102-103`, `:108-112`). Le même message apparaît en 2021 dans les tests de nix-du construits par nixpkgs (S6). La correspondance avec le constat de 495 du 11 octobre est exacte.
   - *Linux : emboîtement réel.* Le test `nested-sandboxing.sh` lance Nix dans une construction confinée, sur cinq niveaux, avec un magasin déplacé par niveau (`nested-sandboxing.sh:24-26`, `nested-sandboxing/command.sh:27-34`). Il exige que le `sandbox-build-dir` ne contienne pas le magasin, et vérifie l'erreur dans le cas contraire (`nested-sandboxing.sh:24`). Sous macOS, un magasin déplacé est refusé (« not supported on this platform », `unix-derivation-builder.cc:1088-1096`). S8 en donne la raison, selon un mainteneur : Seatbelt filtre des chemins mais ne peut pas les remapper.
   - *Détection par sonde, pas par déclaration.* Linux essaie `clone(CLONE_NEWUSER)`, puis un remontage de `/proc` dans de nouveaux espaces de noms (`linux-namespaces.cc:16-90`). Les tests sautent avec un message qui dit quoi changer (« Run 'sudo sysctl -w …apparmor_restrict_unprivileged_userns=0' », `functions.sh:361-365` ; `requireSandboxSupport`, `:157-163` ; sonde `unshare`, `vars.sh:78-80`).
   - *Repli silencieux.* Quand les espaces de noms manquent, `sandbox-fallback` (vrai par défaut) **désactive le bac à sable** avec un avertissement unique, au lieu d'échouer (`local-settings.hh:418-419`, `unix-derivation-builder.cc:1098-1116`). C'est l'inverse du `capability_missing` de 495.
   - Les propriétés de sécurité sont testées dans des VM NixOS : setuid, accès au dossier d'une autre construction, fuite de descripteur d'une sortie fixe (`tests/nixos/setuid.nix:1`, `tests/nixos/user-sandboxing/`, `tests/nixos/ca-fd-leak/`). Seuls certains tests en VM tournent dans la CI GitHub, et sous Linux seulement (`ci.yml:113-118`, `ci/gha/tests/default.nix:323-337`). Où tournent les autres : la source lue ne le dit pas.

6. **Frontière pour un bac à sable ou Docker.**
   - *Une machine dotée d'une capacité, choisie par étiquette.* Une dérivation déclare `requiredSystemFeatures`. Nix ne la construit que sur une machine dont `system-features` les contient, localement (`derivation-building-goal.cc:403-411`) ou sur un constructeur distant (`builders`, champs 6 et 7 : capacités offertes et obligatoires, `worker-settings.hh:197-203`, `build-remote.cc:143-170`). Le constructeur distant est joint en SSH et exige que l'utilisateur SSH soit dans ses `trusted-users` (`distributed-builds.md:11-19`). Il construit sous sa propre configuration ; il reçoit la même dérivation, donc la même révision des entrées.
   - *La VM comme frontière, à l'intérieur du bac.* Un test NixOS est une dérivation ordinaire, construite dans le bac à sable (sans réseau : « NixOS tests run isolated from the network », S2 `run.nix:124-133`). Elle démarre des VM QEMU et requiert `nixos-test`, `kvm` sous Linux et `apple-virt` sous macOS (S2 `run.nix:33-70`, `:161`). Elle requiert `uid-range` pour des conteneurs systemd-nspawn, et `devnet` si VM et conteneurs communiquent, ce qui exige `/dev/net` dans `extra-sandbox-paths` (S2 `run.nix:36-57`). `/dev/kvm` entre dans le chroot de **toute** construction d'une machine qui annonce `kvm`, pas seulement de celles qui le demandent (`linux-derivation-builder.cc:759-767`, `derivation-builder.hh:113-119`, `derivation-building-goal.cc:976`). `uid-range` donne 65 536 UID et root dans l'espace de noms utilisateur, ainsi que `/sys` (`globals.hh:347-354`, `linux-derivation-builder.cc:843-848`).
   - *Docker / Testcontainers.* La source ne le traite pas ; aucune voie vers un démon Docker de l'hôte n'est prévue dans le code lu. La seule voie documentée vers des conteneurs est nspawn dans le bac via `uid-range`.
   - *Sortie fixe et réseau.* Sous Linux, une sortie fixe garde le réseau de l'hôte (pas de `CLONE_NEWNET`), reçoit `resolv.conf`, `hosts`, `services` et le fichier d'AC (`linux-derivation-builder.cc:580-581`, `:783-801`). Sous macOS, `sandbox-network.sb` est ajouté (`darwin-derivation-builder.cc:90-93`). En `relaxed`, une sortie fixe tourne sans bac du tout (`local-settings.hh:389-391`). La contrepartie : hachage vérifié et aucune référence au magasin (`derivation-check.cc:21-40`). Sous Linux, Landlock isole en plus les sockets abstraites entre sorties fixes (`linux-derivation-builder.cc:224-230`).
   - *Réseau local sous macOS.* La règle `(allow network* (local ip))` laissait passer tout le trafic. Elle a été remplacée par `(remote ip "localhost:*")` en 2024 (S4, `sandbox-defaults.sb:53-54`). Un `sendfile` reste refusé même avec le réseau local (S3, 2025-12-10).

7. **Coût.**
   - *Plateformes.* Linux, macOS, FreeBSD. Sous un autre système, une construction confinée est refusée (`unix-derivation-builder.cc:1121-1138`).
   - *Préparation.* Démon root, groupe de comptes de construction, `/nix/store` en `1775` (`local-settings.hh:286-319`, `:384-387`). Sous Linux : espaces de noms utilisateur non privilégiés, que la CI débloque à la main sur Ubuntu 24.04 (`ci.yml:104-106`).
   - *Entretien macOS.*
     - Le profil liste chaque entrée du magasin. Au-delà de 65 535 octets de motifs, Seatbelt refuse (S5, 2020, toujours ouvert) ; Nix découpe la liste en blocs de 16 Kio (`darwin-derivation-builder.cc:106-115`).
     - Les autorisations s'accumulent au fil des versions de macOS : `/private/var/select/sh` pour 10.15, Rosetta, `SystemVersionCompat.plist` (`sandbox-defaults.sb:41-115`).
     - Le bac complet reste désactivé par défaut sur macOS. En 2022, les Mac de Hydra tournaient en `sandbox = false`, parce que « enabling the full sandbox on macOS breaks building a lot of applications ». Un test a saturé le réseau et valu une plainte pour abus (S3). L'état actuel de Hydra n'est pas lu.
   - *Temps de démarrage.* Aucune mesure dans la source lue.

**Pour 495.**
- *Reprendre (constaté dans S1).* Nix ne superpose pas un second Seatbelt : il l'éteint dans la couche intérieure, et compte sur la couche extérieure (`test-main.cc:37-42`, `vars.sh:47-49`). Déduction : un test de 495 qui démarre un bac à sable peut détecter qu'il tourne déjà sous le profil de 495 (une variable posée par 495, comme `NIX_STORE`). Il exécuterait alors sous le profil extérieur, qui reste en vigueur, au lieu d'échouer. Cela ne viole pas la règle « jamais sans confinement ». Mais ce test ne prouve plus rien du profil intérieur. Ce qui vérifie vraiment le profil doit tourner hors confinement, ailleurs, sur la même révision : c'est le besoin (2).
- *Reprendre (constaté dans S1 et S2).* Pour le besoin (2), le contrôle déclare une étiquette de capacité (`docker`, `nested-sandbox`, à l'image de `requiredSystemFeatures`). Seul un exécuteur qui l'annonce dans sa configuration, écrite par le propriétaire, le prend en charge. Nix montre aussi que la frontière la plus solide pour du code qui démarre des services est une VM, lancée **depuis** le bac à sable (tests NixOS). Il n'ouvre pas le bac à l'hôte.
- *Reprendre (constaté dans S1).* La séparation des auteurs répond au besoin (1) : la dérivation, comme le candidat, *demande* ; la configuration, comme le propriétaire, *borne*. Le refus nomme le réglage à changer (« not in allowed-impure-host-deps »). Pour 495, déduction : un droit demandé par le dépôt cible ne vaudrait que dans une liste de préfixes que le propriétaire a acceptée hors du code candidat. Le message de refus citerait la clé à ajouter.
- *Reprendre (constaté dans S1).* Deux gestes simples, pour l'environnement et les liens. Un `HOME` inexistant plus `GIT_CONFIG_GLOBAL=/dev/null` et `GIT_CONFIG_SYSTEM=/dev/null` traitent exactement la panne de signature git de 495. Le montage `O_NOFOLLOW` composant par composant, avec les liens recréés et non suivis, est le modèle d'un droit d'écriture qui ne s'étend pas par un lien committé.
- *Écarter (constaté dans S1).* Deux mécanismes contredisent les besoins de 495. `sandbox-fallback`, vrai par défaut, désactive le bac en silence quand le noyau ne suit pas : 495 doit garder `capability_missing`. `__darwinAllowLocalNetworking`, qu'une dérivation s'accorde sans garde, est l'exemple de ce que le candidat ne doit pas pouvoir écrire. 495 écrit déjà la règle réseau locale sous la forme corrigée par S4 (`(remote ip "localhost:*")`, `src/adapters/sandbox/backends.ts:154-156`, vérifié dans le dépôt de 495).
