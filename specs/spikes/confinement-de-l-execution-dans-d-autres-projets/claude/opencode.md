**Permission applicative ou confinement par le système.** Une permission applicative est une décision que l'agent prend lui-même avant d'appeler un outil. Il lit les arguments de l'appel — le texte d'une commande, un chemin, une URL — et les confronte à des règles. Il exécute, demande ou refuse. Une fois l'appel accepté, le processus lancé a tous les droits de l'utilisateur. Un confinement par le système agit plus bas : le noyau (Seatbelt, espaces de noms, Landlock, seccomp) refuse un appel système (`open`, `connect`, `execve`) à tout processus du bac à sable, sous quelque forme que la demande arrive. La permission juge ce que l'appel annonce. Le confinement juge ce que le processus fait. OpenCode ne fournit que la première ([S1] `SECURITY.md:15-19`).

1. **Ce qui est confiné.** Rien au niveau du système. `SECURITY.md` le dit en toutes lettres : « OpenCode does **not** sandbox the agent. The permission system exists as a UX feature [...] it is not designed to provide security isolation » ; pour un vrai isolement, lancer OpenCode dans un conteneur Docker ou une VM ([S1] `SECURITY.md:15-19`). Les évasions du bac à sable sont hors du périmètre des signalements de sécurité, tout comme le comportement des serveurs MCP et les fichiers de configuration malveillants ([S1] `SECURITY.md:28-33`). Le contrôle porte sur chaque outil, avant l'appel : `read`, `edit` (couvre `write` et `patch`), `glob`, `grep`, `bash`, `task`, `skill`, `webfetch`, `external_directory`… ([S2] `permissions.mdx:152-168`). L'outil shell analyse le texte de la commande avec tree-sitter, demande la permission pour chaque commande trouvée, puis lance le shell ([S1] `tool/plugin/shell.ts:117-155`, `shell/parse.ts:175-206`). Le processus est lancé détaché, avec l'environnement du serveur ([S1] `shell.ts:259-307`). Ce que ce processus lance ensuite n'est plus examiné : l'analyse ne voit que la ligne de commande (déduction du code lu). Les plugins exécutent du code arbitraire : « Provider policy is not a full sandbox for executable plugins » ([S1] `specs/v2/provider-policy.md:248`).
   Ce qu'une permission laisse passer, d'après le code (déductions, non essayées) :
   - `npm *` autorisé laisse `npm test` exécuter tout script du `package.json`, avec tous les droits de l'utilisateur. La règle a jugé le texte `npm test`, pas ce que fait le script.
   - Pour une commande shell, seuls les arguments de `cd`, `pushd`, `popd`, `chdir`, `set-location` et `push-location` passent le contrôle `external_directory` ([S1] `shell/parse.ts:14`, `191-195`). Un `cat ~/.ssh/id_rsa` ne relève que de la règle `bash`, appliquée au texte.
   - Un argument de `cd` qui contient `$`, un accent grave ou `(` est écarté du contrôle, sans demande ([S1] `shell/parse.ts:306-312`, `357-361`).
   - Les chemins sont jugés lexicalement : `path.resolve` puis une inclusion textuelle ([S1] `file-access.ts:93-99`, `packages/util/src/fs-util.ts:280-283`). Un lien du projet vers l'extérieur se modifie avec la seule permission du projet. C'est voulu et testé : « edits an external symlink target with only its in-location permission » ([S1] `test/tool-edit.test.ts:239-272`) et « resolves a prospective target below an external symlink lexically » ([S1] `test/file-access-path.test.ts:113-127`).
   Un confinement par le système laisserait passer, lui, tout ce que son profil permet, mais il le refuserait aussi au script de `npm test`, au lien symbolique ou au processus petit-fils.

2. **Droits.** *Déclaration.* Une clé `permission` dans `opencode.json`, globale ou par outil. Une valeur peut être un objet de motifs (`*` et `?`, `~` et `$HOME` développés). La dernière règle qui correspond l'emporte ([S2] `permissions.mdx:42-111` ; [S1] `permission.ts:87-97`). Les règles d'un agent s'ajoutent à la configuration globale et l'emportent sur elle ([S2] `permissions.mdx:207-241` ; [S1] `permission.ts:158-163`). Un agent sans permissions reçoit `* : deny` ([S1] `permission.ts:19`, `162`). La variable `OPENCODE_PERMISSION` permet d'injecter la configuration en JSON ([S2] `cli.mdx:691`).
   *Découverte.* Par demande, avant l'appel, pas à partir d'un refus du système. Il n'existe ni journal de refus ni mode apprentissage, puisqu'aucun refus du système n'existe.
   *Accord.* L'utilisateur, dans l'interface. `once` vaut pour cette demande, `always` pour les motifs proposés par l'outil, `reject` refuse ([S2] `permissions.mdx:195-203`). Pour le shell, le motif proposé est un préfixe de commande calculé sur une table d'arités, par exemple `git status *` ou `npm run x *` ([S1] `shell/parse.ts:23-161`, `375-381`). La documentation dit qu'`always` dure « for the rest of the current OpenCode session » ([S3]). Le code, lui, écrit la règle dans une table SQLite `permission`, par projet ([S1] `permission.ts:299-305`, `permission/saved.ts:63-75`, `permission/sql.ts`). Je n'ai pas vérifié si cette base survit à la session. Un refus accompagné d'un message est renvoyé au modèle comme correction ([S1] `permission.ts:276-280`). Le drapeau `--auto` approuve toute demande qui n'est pas explicitement refusée ([S2] `permissions.mdx:22-36`). Un plugin peut réécrire la décision par le crochet `permission.evaluate` ([S1] `permission.ts:179-188`).

3. **Refusé quoi qu'on déclare.** Au niveau du système, rien. Au niveau de l'application, deux règles tiennent. Un `deny` configuré tient même sous `--auto` ([S2] `permissions.mdx:36`). Il tient aussi contre une approbation `always` déjà enregistrée : le refus est évalué sur les règles configurées avant l'ajout des règles enregistrées ([S1] `permission.ts:173-178`). La documentation annonce `.env` refusé par défaut, et `external_directory` et `doom_loop` en `ask` ([S2] `permissions.mdx:172-191`). Au commit lu, l'agent par défaut porte `* : allow` et `read *.env : ask`, pas `deny` ([S1] `packages/schema/src/agent.ts:46-51`). Je n'ai trouvé de règle `external_directory : ask` par défaut ni dans `packages/core/src` ni dans `packages/schema/src`. `doom_loop` n'y apparaît que dans la migration de la configuration v1 ([S1] `v1/config/permission.ts:27`). La documentation et le code divergent donc sur ces valeurs par défaut.

4. **Environnement de l'hôte.** Il n'est pas tenu à l'écart. Le shell reçoit `process.env` en entier, plus `TERM`, `OPENCODE_TERMINAL`, `AGENT=1`, `OPENCODE=1`, `OPENCODE_SESSION_ID` ([S1] `shell.ts:259-272`, `tool/plugin/shell.ts:213-216`). Un plugin peut ajouter des variables par le crochet `shell.env` ; l'exemple de la documentation injecte une clé d'API ([S2] `plugins.mdx:193`, `261-266`). Aucun filtrage de variable ni redirection de `HOME` n'apparaît dans le code lu. `~/.gitconfig`, `~/.ssh` et les caches de paquets restent ceux de l'utilisateur (déduction : environnement hérité et aucun confinement). La source ne dit rien de la configuration git.

5. **Tester sous confinement.** Sans objet : OpenCode ne démarre aucun bac à sable. Les tests du moteur de permissions sont des tests unitaires sur des montages simulés (par exemple `test/tool-edit.test.ts`). La source ne traite pas de l'emboîtement.

6. **Frontière pour un bac à sable ou Docker.** Celle que l'utilisateur pose autour d'OpenCode. `SECURITY.md` renvoie à Docker ou à une VM ([S1] `SECURITY.md:19`), et la documentation d'installation publie une image (`docker run -it --rm ghcr.io/anomalyco/opencode`, [S2] `index.mdx:127-131`). Une seconde voie est expérimentale (`OPENCODE_EXPERIMENTAL_WORKSPACES`, [S2] `cli.mdx:733`) : un « workspace driver » fourni par celui qui embarque OpenCode. Ce pilote remplace le lanceur de processus et les opérations de fichiers par celles d'un environnement distant ([S1] `workspace/driver.ts:26-62`, `environment/driver.ts:4-7`). Le registre par défaut est vide ([S1] `workspace/driver.ts:88`) et se remplit par l'option `workspaceProviders` du SDK ([S1] `packages/sdk/src/internal/host.ts:21`, `43-44`). Dans ce mode, le shell ne reçoit pas l'environnement de l'hôte ([S1] `shell.ts:259-262`). Le dépôt ne contient aucun pilote concret.

7. **Coût.** Pour les permissions : une analyse de la commande par tree-sitter en WebAssembly, chargée une fois ([S1] `shell/parse.ts:389-403`), et des demandes à l'utilisateur. Elles couvrent toutes les plateformes d'OpenCode, PowerShell compris ([S1] `shell/parse.ts:15-16`, `209-288`). Pour l'isolement réel, le coût est celui de Docker ou de la VM. La source ne le chiffre pas.
