1. **Ce qui est confiné.** Chaque conteneur tourne dans sa propre VM Linux légère, sur Virtualization.framework [S1 `technical-overview.md:24-30` ; S2 `README.md:25-32`].
   - La frontière est la VM : tout ce qui y tourne est confiné, processus enfants compris. Le système de fichiers de l'hôte n'y paraît que par montage explicite [S1 `technical-overview.md:28-29`].
   - Dans la VM, le processus du conteneur a ses espaces de noms cgroup, IPC, montage, PID et UTS, sans espace de noms utilisateur [S2 `LinuxContainer.swift:503-509`].
   - Les capacités Linux sont celles d'un conteneur OCI par défaut, sans `CAP_SYS_ADMIN` [S1 `runtime-configuration.md:8-10`]. Les chemins sensibles de `/proc` et `/sys` sont masqués ou en lecture seule [S1 `runtime-configuration.md:55-63`]. Le filtre seccomp vaut `unconfined` par défaut dans le framework [S2 `LinuxContainer.swift:57-81`, `:120-122`].
   - Côté hôte, la CLI parle par XPC à `container-apiserver`, un agent launchd. Celui-ci lance un assistant `container-runtime-linux` par conteneur [S1 `technical-overview.md:43-47`]. La VM n'est donc pas un processus enfant de la CLI. Ces assistants portent l'autorisation `com.apple.security.virtualization` [S1 `signing/container-runtime-linux.entitlements`].
   - *« Container machine ».* Ce mode lève l'essentiel de l'isolement. Il monte `$HOME` en lecture-écriture au même chemin, transmet l'agent SSH, accorde toutes les capacités, ne masque rien et donne `sudo` sans mot de passe [S1 `container-machine.md:5-13`]. La doc le dit proche d'un programme lancé directement sur l'hôte.

2. **Droits.** Tout se déclare à la ligne de commande, par l'appelant. Aucun fichier de l'image ni du projet ne les élargit.
   - *Fichiers.* `--volume source:cible[:ro]` ou `--mount type=bind|volume|tmpfs,…,readonly` [S1 `volumes.md:9-32`, `:202-232`], `--read-only` pour la racine, `--tmpfs` [S1 `command-reference.md:62`, `:70`, `:77`].
   - *Capacités.* `--cap-add` / `--cap-drop` [S1 `runtime-configuration.md:12-48`].
   - *Réseau.* Le réseau `default` par défaut, des réseaux isolés entre eux (`container network create`, macOS 26) [S1 `networking.md:6-9`, `:155-176`]. `--network none` détache le conteneur de tout réseau et ne se combine avec aucun autre [S1 `Utility.swift:199-204`].
   - *Agent SSH.* `--ssh` le transmet, sinon rien [S1 `host-integration.md:6-10` ; `RuntimeService.swift:80-94`].
   - *Découverte d'un droit manquant.* La source n'en prévoit aucune. Un refus se lit comme une erreur Linux ordinaire dans le conteneur, par exemple `Operation not permitted` ou `Read-only file system` [S1 `runtime-configuration.md:45-48`, `:67-71`].
   - *Liens symboliques.* Pour monter un fichier seul, le framework résout ses liens. Il partage ensuite **tout le répertoire parent** en virtiofs, puis lie le fichier dans le conteneur [S2 `FileMount.swift:20-27`, `:132-135`]. Pour un répertoire, la source ne dit pas si les liens qu'il contient et qui pointent hors du partage sont suivis côté hôte. Ce que j'en déduis : la VM ne voit que les répertoires partagés, et un lien vers `~/.ssh` y serait résolu dans le système de fichiers de la VM, pas sur l'hôte. Non vérifié dans le code de virtiofs, non essayé.

3. **Refusé quoi qu'on déclare.** La source ne décrit pas de plancher au sens d'une liste de chemins interdits : ce qui n'est pas monté n'existe pas dans la VM. Les nuances :
   - `--cap-add ALL`, `--masked-path NONE` et `--read-only-path NONE` lèvent toutes les protections internes à la VM [S1 `runtime-configuration.md:23-35`, `:73-83`]. La frontière VM ↔ hôte reste.
   - La virtualisation emboîtée est refusée si la machine ne la supporte pas : `Error: unsupported: "nested virtualization is not supported on the platform"` [S1 `runtime-configuration.md:94-99`].
   - La variable d'environnement d'une image n'est jamais complétée depuis l'hôte : « Image config is untrusted » [S1 `Parser.swift:170-174`].

4. **Environnement de l'hôte.**
   - Le processus reçoit l'environnement de l'image, les fichiers `--env-file`, puis `--env` [S1 `Parser.swift:170-187`]. Une variable passée sans `=` est copiée de l'hôte. Une variable absente de l'hôte est ignorée [S1 `Parser.swift:271-286`]. L'exemple de la doc montre l'environnement complet d'un conteneur : `HOME=/root`, `PATH` de l'image, et `SSH_AUTH_SOCK` seulement avec `--ssh` [S1 `host-integration.md:13-20`].
   - La CLI lit `SSH_AUTH_SOCK` de l'hôte à chaque `run` [S1 `ContainerRun.swift:132-135`]. Le service ne monte la socket que si le conteneur a été créé avec `--ssh` [S1 `RuntimeService.swift:85-94`].
   - `~/.gitconfig`, les clés et les caches de l'hôte n'entrent que par un `--volume` explicite. La source ne traite pas des caches de paquets ; un volume nommé persiste entre deux exécutions [S1 `volumes.md:34-65`].
   - *Exception.* Le mode « container machine » monte tout `$HOME` en lecture-écriture (§ 1).

5. **Tester sous confinement.**
   - *Le cas de 495 : un processus de l'hôte sous Seatbelt pilote `container`.* S3 décrit un appelant sous `sandbox-exec` avec un profil `(deny default)`. Ce profil autorise `mach-lookup` vers quatre services : `com.apple.container.apiserver`, `…core.container-core-images`, `…core.machine-apiserver` et `…network.container-network-vmnet.default`. Dans ce cadre, `container run --rm alpine echo hi` fonctionne de bout en bout. Seul `container system status` répondait faux, parce qu'il interrogeait launchd par une voie qui exige le droit Seatbelt `job-creation`. C'est corrigé : la sonde de santé passe désormais avant [S3, commentaires du 2026-09-29 et du 2026-09-30].
   - *Ce que j'en déduis.* Lancer une VM depuis un processus confiné ne demande pas d'emboîter Seatbelt. Le profil externe doit seulement ouvrir quelques services XPC, puisque la VM est lancée par un agent launchd hors du bac à sable. Mais ces mêmes services permettent au processus confiné de créer un conteneur avec `--volume $HOME:$HOME`. Le droit `mach-lookup` vers l'apiserver vaut donc l'accès à tout ce que l'utilisateur peut monter. Non essayé.
   - *Emboîtement de bacs à sable dans la VM.* Le framework a des options pour **affaiblir** le confinement de ses propres composants quand ils tournent eux-mêmes dans un conteneur `container --virtualization` : seccomp de cloud-hypervisor, et espace de noms utilisateur plus `pivot_root` de virtiofsd [S2 `SandboxOverrides.swift:17-50`]. Sa suite d'intégration Linux les active toutes [S2 `Makefile:291`]. Le commentaire précise : « only enable this when the parent process is the trust boundary you want » [S2 `SandboxOverrides.swift:44-46`].

6. **Frontière pour un bac à sable ou Docker.**
   - *Docker dans la VM.* C'est possible, avec réserves. Le noyau Kata installé par défaut n'active pas `CONFIG_NF_TABLES`, et `dockerd` échoue sur `iptables` [S4, commentaire de dcantah, 2026-01-01]. Deux parades sont citées : `iptables-legacy` dans l'image, ou un noyau construit depuis `containerization/kernel` [S4]. Un participant y fait tourner Docker Engine 29.1.5 avec containerd et runc [S4, commentaire du 2026-01-24]. Le mainteneur précise que `container` n'embarque pas de noyau et a choisi celui de Kata, « missing features for some workloads, including Docker Engine » [S4, jglogan, 2026-01-02].
   - La configuration du noyau du dépôt Containerization active les espaces de noms utilisateur, PID et réseau, KVM, seccomp, netfilter, nf_tables, bridge et veth [S2 `kernel/config-arm64:185-191`, `:618-619`, `:666-667`, `:1070`, `:1119`, `:1419`, `:1936`]. Ce n'est pas le noyau par défaut [S1 `container-system-config.md:34-35`].
   - *Testcontainers depuis l'hôte.* Non pris en charge : il faudrait une API compatible Docker, et l'équipe n'a pas prévu d'en fournir [S5, jglogan, 2025-09-15].
   - *Bubblewrap dans la VM.* La source ne le dit pas. Les éléments lus ne l'excluent pas, mais rien ne l'atteste ; c'est une déduction, non essayée. Le processus y est root, sans `CAP_SYS_ADMIN`, avec un seccomp `unconfined` par défaut et sans espace de noms utilisateur imposé (§ 1).
   - *Virtualisation emboîtée.* `--virtualization` expose KVM au conteneur. Il faut une puce M3 ou plus récente et un noyau compilé avec `CONFIG_KVM=y`, que le noyau par défaut n'a pas [S1 `runtime-configuration.md:87-111`, `container-machine.md:86-102` ; S2 `README.md:48` ; S6].
   - *Récupérer sortie et code de retour.* `container run` relaie stdout et stderr, puis sort avec le code du processus du conteneur ; une erreur de lancement remonte comme erreur de la CLI, après suppression du conteneur [S1 `ContainerRun.swift:172-180`]. Dans le framework, `vminitd` est le PID 1 de la VM. Il expose une API gRPC sur vsock et renvoie l'I/O, les signaux et les événements au processus appelant [S2 `README.md:29-32`]. `LinuxProcess.wait()` rend un `ExitStatus` (code et date de sortie) [S2 `LinuxProcess.swift:460-480`, `ExitStatus.swift:19-36`].
   - *Limite ouverte.* Un exécutable introuvable et un vrai `exit(255)` rendent tous deux 255, sans moyen de les distinguer par l'API [S8].

7. **Coût.**
   - *Plateformes.* Mac Apple silicon uniquement, macOS 26 pris en charge [S1 `README.md:16-20`]. macOS 15 fonctionne avec des limites réseau [S1 `technical-overview.md:61-77`]. Containerization a aussi un moteur Linux (cloud-hypervisor + KVM, `virtiofsd`), qui demande `/dev/kvm` et un réseau TAP préparé par l'appelant [S2 `README.md:34-46`].
   - *Préparation.* Il faut un paquet signé installé avec le mot de passe administrateur sous `/usr/local`, puis `container system start` [S1 `README.md:22-32`]. Le noyau est téléchargé au premier démarrage, depuis une archive Kata [S1 `container-system-config.md:34-35`, `:106-107`].
   - *Démarrage.* La doc annonce un démarrage en moins d'une seconde [S2 `README.md:27`], et des temps « comparables » à ceux d'une VM partagée [S1 `technical-overview.md:30`]. Aucune mesure n'est publiée dans les sources lues.
   - *Mémoire.* La mémoire libérée dans la VM n'est pas rendue à macOS ; la doc conseille de redémarrer les conteneurs gourmands [S1 `technical-overview.md:55-59`].
   - *Entretien et fiabilité sur cette machine (macOS 27).* Un ticket ouvert décrit, sous macOS 27.0, un `container system start` bloqué indéfiniment, comme toute autre commande, quand aucun processus ne tient de référence au pare-feu `pf`. La cause est extérieure à `container`. Le rapporteur la contourne en activant le mode furtif du pare-feu puis en redémarrant [S7]. Ce que j'en déduis : un appel à `container` doit porter son propre délai d'expiration. La compatibilité n'est garantie qu'à l'intérieur d'une version majeure [S1 `README.md:100-109`].

**Pour 495.**
- *Reprendre comme backend « ailleurs » sous macOS.* (Besoin 2.) Une VM par contrôle, lancée par un agent launchd hors du Seatbelt de l'appelant [S1, S3]. Elle évite l'emboîtement que `sandbox-exec` refuse, et le code de retour revient par `container run` [S1 `ContainerRun.swift:180`]. Ce que j'en déduis : un test de 495 qui démarre un bac à sable pourrait y tourner sous bubblewrap, mais seulement après essai, puisque la source ne l'atteste pas. Docker pour Testcontainers y tournerait avec un noyau non par défaut ou `iptables-legacy` [S4].
- *Adapter : ne rien monter que la copie, en lecture-écriture, et jamais de `$HOME`.* (Besoin 1.) Chez `container`, les droits sont des arguments de l'appelant, jamais lus dans l'image ou le projet. L'environnement de l'image n'est pas complété depuis l'hôte [S1 `Parser.swift:172-174`]. Rien de l'hôte n'entre sans montage, ni `~/.gitconfig` ni clé. C'est le contraire du mode « container machine » [S1 `container-machine.md:5-13`], à écarter. Attention : monter un fichier seul expose tout son répertoire parent à la VM [S2 `FileMount.swift:20-27`].
- *Écarter l'idée qu'ouvrir l'apiserver au contrôle confiné soit sans risque.* Ce que j'en déduis de S3 : si 495 confine un contrôle sous Seatbelt et lui ouvre les services XPC de `container`, ce contrôle peut créer une VM qui monte n'importe quel répertoire de l'utilisateur. Le lancement de la VM doit donc rester au noyau de 495, hors du contrôle, avec des montages fixés par 495.
- *Coût à peser.* Apple silicon et macOS 26 ou plus seulement, une installation administrateur, et un démon dont le démarrage peut bloquer sans fin sous macOS 27 [S7]. Les codes de retour de `container` ne distinguent pas tous les échecs de lancement [S8]. Ce backend ne remplace donc pas bubblewrap sous Linux ; Containerization a bien un moteur Linux, mais il exige KVM [S2 `README.md:42-46`].
