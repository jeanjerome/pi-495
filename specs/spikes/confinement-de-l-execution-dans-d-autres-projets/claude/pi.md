1. **Ce qui est confiné.** Pi seul ne confine rien. Il lit, modifie et exécute avec les droits du compte qui l'a lancé, sans approbation par appel ; extensions, installeurs et processus enfants ont ces mêmes droits [S1 `security.md:3`]. L'absence de bac à sable intégré est hors du périmètre de sécurité déclaré [S1 `security.md:99`]. Pi décrit quatre montages [S1 `containerization.md:9-14`] : Pi entier dans Docker, dans Docker Sandboxes ou dans OpenShell (Pi, outils, commandes `!` et extensions confinés), ou Pi sur l'hôte avec ses seuls outils intégrés routés dans une VM Gondolin. Dans ce dernier cas, Pi et les outils des autres extensions restent sur l'hôte [S1 `containerization.md:16`, `:26`, `:183`].
   - L'exemple « sandbox » ne remplace que l'outil `bash` et les commandes `!` [S2 `index.ts:214-232`]. `read`, `write` et `edit` restent hors confinement.
   - L'exemple Gondolin livré avec Pi remplace `read`, `write`, `edit`, `bash`, `grep`, `find`, `ls` et les commandes `!` [S3 `index.ts:443-520` ; S1 `containerization.md:181`].
   - `pi.exec()`, offert aux extensions, lance un `spawn` direct sur l'hôte, sans option d'environnement ni de confinement [S5 `exec.d.ts:7-14`, `exec.js:12-16`].
   - Dans Gondolin, tout le code du guest tourne dans une VM Linux (QEMU par défaut, libkrun en option expérimentale) [S6 `README.md:8-9` ; `docs/security.md:110-123`].

2. **Droits.**
   - *Exemple sandbox.* Les droits se déclarent en JSON (`network.allowedDomains`/`deniedDomains`, `filesystem.denyRead`/`allowWrite`/`denyWrite`). Pi lit d'abord `~/.pi/agent/extensions/sandbox.json`, puis `<cwd>/.pi/sandbox.json`, et le projet l'emporte [S2 `index.ts:12-30`, `:79-103`]. Les valeurs par défaut sont aux lignes `:55-77`. La fusion est superficielle par section : un `filesystem` de projet remplace les listes par défaut clé par clé [S2 `index.ts:109-114`]. Aucune découverte d'un droit manquant n'est prévue. La seule interface est `/sandbox`, qui affiche la configuration [S2 `index.ts:297-319`]. `ignoreViolations` est transmis tel quel à la bibliothèque [S2 `index.ts:116-127`, `:264-269`].
   - *Ce que j'en déduis.* `.pi/sandbox.json` ne figure pas dans la liste des ressources soumises à la confiance de projet [S1 `security.md:37-45`]. Un fichier écrit dans la copie par le code candidat peut donc élargir les droits, ou poser `"enabled": false` [S2 `index.ts:245-249`].
   - *Accord humain.* Le moyen fourni est l'événement `tool_call` avec `ctx.ui.select` ou `ctx.ui.confirm`. Sans interface, l'exemple bloque par défaut [S4 `permission-gate.ts:13-33`]. `project_trust` décide du chargement des ressources d'un dossier, avec mémorisation dans `~/.pi/agent/trust.json` [S1 `security.md:59-73` ; S4 `project-trust.ts:26-59`].
   - *Gondolin.* Les droits se déclarent dans le code hôte : montages VFS (`RealFSProvider`, `ReadonlyProvider`, `ShadowProvider`, `MemoryProvider`) et `createHttpHooks({ allowedHosts, secrets })` [S6 `docs/security.md:254-273`, `docs/vfs.md:77-173`, `README.md:15-28`]. Les docs lues ne décrivent aucun mode apprentissage ni aucune découverte d'un droit à partir d'un refus : la source ne le dit pas. Sans `httpHooks`, aucune règle par requête n'est appliquée [S6 `host/src/qemu/http.ts:2145`]. Avec `createHttpHooks`, `allowedHosts` vaut `["*"]` par défaut [S6 `host/src/http/hooks.ts:160-163`]. L'exemple Pi n'en passe pas [S3 `index.ts:381-388`] : le guest y atteint donc tout hôte public en HTTP/HTTPS.

3. **Refusé quoi qu'on déclare.**
   - *Pi.* Rien n'est refusé. *Exemple sandbox.* Aucun plancher : le projet peut vider `denyRead` ou désactiver le bac à sable (§ 2).
   - *Gondolin, refus de protocole.* Sont refusés : tout TCP non classé HTTP, TLS ou SSH autorisé (`unknown-protocol`), `CONNECT`, et tout UDP sauf le port 53 [S6 `docs/security.md:137-152`]. Restent aussi hors de portée HTTP/2, HTTP/3 et QUIC [S6 `docs/limitations.md:35-48`].
   - *Gondolin, réglables mais actifs par défaut.* Les plages internes (127/8, RFC1918, 169.254/16…) sont bloquées, même sans `httpHooks` [S6 `docs/security.md:173-177` ; `docs/network.md:263-271`]. On peut le lever par `blockInternalRanges: false`.
   - *Gondolin, `RealFSProvider`.* Il bloque toujours les liens qui sortent du répertoire monté et les liens pendants lors d'une opération qui suit le lien. Il abandonne les bits setuid/setgid sur l'hôte [S6 `docs/vfs.md:99-103`]. Côté code, la racine est canonisée par `realpath`, puis chaque chemin suivi est résolu par `realpath` et comparé à la racine ; à défaut, le premier ancêtre existant est contrôlé [S6 `real.js:189-194`, `:270-301`].

4. **Environnement de l'hôte.**
   - *Outil `bash` de Pi.* Il reçoit `process.env` entier, `PATH` complété, plus `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL` et `PI_REASONING_LEVEL` [S5 `shell.js:115-126`, `bash.js:136-155` ; S1 `environment-variables.md:20-49`]. Un `spawnHook` peut réécrire commande, répertoire et environnement avant l'exécution [S5 `bash.d.ts:64-81` ; S4 `bash-spawn-hook.ts:16-22`].
   - *Exemple sandbox.* Il ignore l'option `env` reçue et lance `bash` sans `env`, donc avec l'environnement complet du processus Pi [S2 `index.ts:134-146`]. Il interdit en lecture `~/.ssh`, `~/.aws` et `~/.gnupg` [S2 `index.ts:73`]. Rien ne vise `~/.gitconfig` ni les caches.
   - *Les deux exemples Gondolin divergent.* La copie livrée avec Pi transmet l'environnement à la VM [S3 `index.ts:315-322`, `:345`], ce que la doc de Pi signale [S1 `containerization.md:157`]. La copie du dépôt Gondolin ne le transmet pas, « it usually contains API keys », et renvoie aux secrets par `httpHooks` [S6 `host/examples/pi-gondolin.ts:118-120`].
   - *Secrets dans Gondolin.* Le guest ne voit qu'un substitut. L'hôte met la vraie valeur dans les en-têtes, et seulement vers les hôtes autorisés [S6 `docs/security.md:217-241`].
   - *Fichiers de l'hôte.* Le guest n'en voit aucun hors montage [S6 `docs/security.md:272-273`]. `/root`, `/tmp` et `/var/cache` y sont des tmpfs [S6 `docs/workloads.md:42`].
   - *Ce que j'en déduis.* `~/.gitconfig`, `~/.npm` et `~/.m2` de l'hôte sont absents par construction, sauf montage explicite. En contrepartie, chaque VM neuve repart sans cache.

5. **Tester sous confinement.**
   - *Pi.* Pi pose `AI_AGENT=pi` et `PI_CODING_AGENT=true`, que les processus enfants héritent [S1 `environment-variables.md:13-18`]. Ce sont des marqueurs d'agent, pas de confinement.
   - *Exemple sandbox.* Il relaie `enableWeakerNestedSandbox` à la bibliothèque [S2 `index.ts:116-127`, `:264-269`]. Son effet n'est pas lu ici (voir « Non lu »).
   - *Gondolin.* Les docs lues ne disent ni comment ses tests tournent sous confinement, ni si QEMU démarre depuis un processus déjà sous Seatbelt : la source ne le dit pas. Elles notent seulement que, sous macOS, « filesystem and sandboxing rules can differ » pour les sockets [S6 `docs/qemu.md:156-163`]. Elles notent aussi que le lanceur krun reçoit l'entitlement `com.apple.security.hypervisor` [S6 `README.md:92-93`].
   - *Ce que j'en déduis.* Le guest est un noyau Linux distinct. Un bac à sable lancé dans le guest n'emboîte donc pas le Seatbelt de l'hôte. Non essayé.

6. **Frontière pour un bac à sable ou Docker.**
   - *Pi* renvoie à un confinement du processus entier : Docker, Docker Sandboxes ou OpenShell [S1 `containerization.md:30-151`].
   - *Gondolin* oppose la frontière QEMU. Une évasion de QEMU compromet l'hôte, et le déni de service n'est pas couvert [S6 `docs/security.md:30-39`, `:427-436`]. Un utilisateur local du même compte peut interférer avec les sockets virtio [S6 `docs/security.md:431-432`].
   - L'image par défaut (Alpine 3.23) contient bash, curl, nodejs, npm, python3, uv et openssh, mais ni git, ni JDK, ni Docker [S6 `images/alpine-base.json:6-22`]. Tout autre paquet exige une image construite [S6 `docs/limitations.md:22-33`].
   - La source ne dit pas si un démon Docker, ou bubblewrap, tourne dans le guest.

7. **Coût.**
   - *Exemple sandbox.* `npm install` de `@anthropic-ai/sandbox-runtime` ; sous Linux, bubblewrap, socat et ripgrep [S2 `index.ts:37-41`]. Plateformes : darwin et linux, sinon désactivé avec un avertissement [S2 `index.ts:251-256`].
   - *Gondolin, prérequis.* QEMU [S6 `README.md:75-79`]. Node ≥ 23.6 selon Pi [S1 `containerization.md:159` ; S3 `index.ts:17-19`], mais `engines.node >=22.19.0` au commit lu [S6 `host/package.json:65-67`].
   - *Gondolin, coût de démarrage.* Environ 200 Mo d'images téléchargées au premier usage puis mises en cache [S6 `README.md:70-73`]. Démarrage « in under a second » [S7 ; S6 `docs/workloads.md:58-59`].
   - *Gondolin, plateformes.* macOS (HVF) et Linux (KVM, `/dev/kvm` requis) ; repli TCG lent [S6 `docs/qemu.md:128-139`]. Pas de Windows [S6 `docs/limitations.md:66-68`]. ARM64 est le chemin le plus testé [S6 `README.md:114-115`]. Images Alpine seulement [S6 `docs/limitations.md:31-33`].
   - *Gondolin, entretien.* Pi épingle 0.12.0 alors que le dépôt est en 0.13.0 [S3 `package.json:17` ; S6 `host/package.json:3`].
   - *Échec du confinement.*
     - L'exemple sandbox revient à l'exécution locale non confinée quand l'initialisation échoue ; il n'émet qu'une notification [S2 `index.ts:218-220`, `:281-284`].
     - La copie Gondolin du dépôt renvoie `undefined` à `user_bash` tant que la VM n'est pas prête [S6 `pi-gondolin.ts:278-279`]. Selon le contrat de Pi, la commande part alors en exécution locale [S1 `extensions.md:127`].
     - La copie livrée avec Pi attend la VM ; si le gestionnaire échoue, la commande est bloquée [S3 `index.ts:517-520` ; S1 `extensions.md:127`].

**Ce que Pi expose à une extension pour confiner ou déléguer l'exécution** (question propre à cette fiche).

Pi ne fournit aucun confinement. Il fournit des points de substitution :
- Les opérations enfichables des outils intégrés. `BashOperations.exec(command, cwd, { onData, signal, timeout, env })` est documenté comme le moyen de « delegate command execution to remote systems » [S5 `bash.d.ts:31-52`]. `ReadOperations`, `WriteOperations`, `EditOperations`, `LsOperations`, `FindOperations` et `GrepOperations` sont exportés [S5 `index.d.ts:26`]. Les exemples Gondolin et SSH s'en servent [S3 ; S4 `ssh.ts:1-14`].
- `createBashTool(cwd, { operations, spawnHook, commandPrefix, exposeSessionEnvironment })` et `createLocalBashOperations()`, pour envelopper l'exécution locale [S5 `bash.d.ts:55-81`].
- L'événement `user_bash`, qui rend `operations` ou un `result` complet ; un échec du gestionnaire bloque la commande [S5 `types.d.ts:863-872`, `:1065-1074` ; S1 `extensions.md:127`].
- L'événement `tool_call`, qui peut modifier l'entrée ou bloquer ; un échec du gestionnaire bloque l'outil [S5 `types.d.ts:1054-1063` ; S1 `extensions.md:105`, `:260`]. Les appels imbriqués par `ctx.executeTool` passent aussi par `tool_call` [S1 `extensions.md:148`]. Les annotations MCP (`readOnlyHint`, `destructiveHint`…) servent d'indices, mais ne sont pas vérifiées [S1 `extensions.md:166-178`].
- Les dialogues `ctx.ui.confirm` et `ctx.ui.select`, gardés par `ctx.hasUI` : interactif et RPC, pas en mode print ni JSON [S1 `extensions.md:242-253`].
- `pi.exec()`, qui ne confine rien et n'accepte pas d'environnement [S5 `exec.d.ts`, `exec.js:12-16`].
