01 / DU CODE GÉNÉRÉ AU CHANGEMENT VÉRIFIÉDU PROMPT AU PROCESSUS

Spécifier. Concevoir.
Tester. Relire.
Avant d’intégrer.

Une fonctionnalité ne se résume pas au code qui l’implémente. Il faut définir son comportement, préserver les interfaces existantes, respecter les dépendances entre modules et vérifier les cas d’erreur.

pi-495 relie les exigences aux tests et aux contrôles qui les vérifient. Les agents préparent les spécifications, la conception et le code ; le noyau exécute les contrôles et applique les critères de passage entre les étapes.

Vous pouvez retrouver ce qui a été demandé, modifié, testé et accepté.

01 — LES AGENTS

Spécifient, conçoivent et codent.

Chaque intervention a un rôle : préciser les exigences, préparer les tests, concevoir la solution, implémenter ou relire. Elle reçoit les documents utiles et les limites de modification.

02 — LE NOYAU

Exécute les contrôles et statue.

Le noyau lance les vérifications, lit leurs rapports et applique les règles d’acceptation. Une déclaration de réussite de l’agent ne remplace pas un résultat de test.

03 — VOUS

Arbitrez les décisions métier.

Vous répondez aux questions qui changent le comportement attendu, tranchez les décisions qui vous sont réservées et autorisez l’intégration. Vos réponses restent rattachées aux exigences.

Cadrage, spécification, qualification, conception, implémentation et acceptation, puis intégration. Chaque étape se termine par une décision fondée sur ses critères de passage, les « quality gates » G0 à G6.

03 / QUALIFIER LES TESTS AVANT L’IMPLÉMENTATIONTESTS DISCRIMINANTS · CONTRÔLES QUALIFIÉS

Un test doit détecter
le défaut qu’il vise.

Avant de confier l’acceptation à un test, il faut vérifier qu’il atteint la bonne assertion et distingue un comportement conforme d’un comportement incorrect. Le processus prévu étend cette qualification à chaque exigence.

01↗

Un moyen de vérification par exigence.

Une exigence est reliée à un test, un contrôle structurel ou une décision humaine. Par exemple, « trois tentatives au total » doit être vérifié en comptant les appels, avec un cas fautif qui en effectue quatre.

02▣

Des tests protégés pendant le codage.

Les tests d’acceptation et leurs critères sont fixés à la qualification. L’agent qui implémente ne peut pas les modifier pour faire passer son code. Un test peut échouer sur la référence précisément parce que la fonctionnalité manque.

03↻

Une procédure pour corriger un test erroné.

Si un test contredit l’exigence, l’agent signale le problème. Le processus prévu impose un examen distinct, une révision justifiée et une nouvelle qualification. Les résultats devenus inapplicables sont invalidés.

Créer une application,

CRÉATION / DU SOCLE À LA RECETTE

Décomposer le produit en incréments vérifiables.

Les spécifications prévoient de partir d’un dépôt vierge : choisir la stack et l’architecture, vérifier le build et les tests, puis livrer les fonctionnalités par incréments. La recette globale vérifie les parcours utilisateur et les échanges entre composants.

  1. 01Préparer un socle qui compile, démarre et exécute ses tests.
  2. 02Affecter les exigences aux incréments et ordonner leurs dépendances.
  3. 03Vérifier les API et les parcours de bout en bout aux jalons.
Deux fonctionnalités testées séparément peuvent rester incompatibles une fois assemblées. La recette de l’application vérifie leur fonctionnement commun.
05 / LES PRATIQUES D’INGÉNIERIE PRÉVUESEXIGENCES · TESTS · ARCHITECTURE · RISQUES

Des pratiques de développement
traduites en vérifications.

Les spécifications prévoient des exigences traçables, des tests qualifiés, des règles d’architecture et des revues adaptées aux risques. Chaque pratique doit produire un résultat que l’on peut examiner.

01
SPÉCIFICATIONS ET CRITÈRES D’ACCEPTATION

Relier l’exigence au résultat de vérification.

Chaque exigence décrit un comportement observable et ses cas d’acceptation. La conception et les tâches indiquent comment la réaliser ; les tests, rapports et revues indiquent comment elle a été vérifiée.

02
TESTS AVANT CODAGE ET TESTS DE MUTATION

Éprouver les assertions, pas seulement compter les tests.

Le test du nouveau comportement doit échouer sur la référence pour la raison attendue. La couverture mesure les lignes exécutées ; la mutation vérifie si les assertions détectent des altérations du code. Les tests par propriétés et le fuzzing sont des compléments prévus.

03
CONSIGNES, CONTRÔLES ET CORRECTIONS

Corriger à partir d’écarts localisés.

L’agent reçoit les exigences, les frontières de modification et les règles du projet. Après vérification, il reçoit les tests en échec et les violations observées. Les tentatives sont limitées et la stagnation provoque un arrêt.

04
ARCHITECTURE ET MIGRATION INCRÉMENTALE

Contrôler les dépendances entre modules.

Le diagnostic compare les modules et leurs dépendances à l’architecture adoptée. Une migration définit des étapes, des interfaces de coexistence et un retour arrière. Les règles de transition empêchent d’ajouter de nouvelles dépendances interdites.

05
ANALYSE ET TRAITEMENT DES RISQUES

Choisir les contrôles selon les risques du changement.

Une migration de données appelle des tests d’intégrité et de reprise. Une API publique appelle des contrôles de compatibilité et de sécurité. Le plan prévoit les tests, expérimentations, revues spécialisées et décisions humaines nécessaires.

06
AMÉLIORATION DU PROCESSUS DE DÉVELOPPEMENT

Mesurer les défauts et les reprises pour améliorer les contrôles.

Le bilan suit les défauts découverts après intégration, les reprises humaines, les délais et les coûts. Une amélioration des consignes ou des contrôles fait l’objet d’un changement séparé, évalué sur des cas de référence.

06 / VÉRIFIER LES TRANSITIONS ET LES INVARIANTSTLA+ · fast-check · Lean

Révision, interruption, reprise.
Vérifier les enchaînements.

Un résultat de test peut arriver après une modification du code. Une reprise peut rejouer une action déjà effectuée. TLA+ explore ces séquences ; fast-check les rejoue sur le noyau réel pour vérifier les invariants du processus.

TLA+ explore les états d’un modèle ; les tests par propriétés exercent le noyau réel ; Lean démontre des propriétés ciblées. Ces moyens sont optionnels et ne deviennent obligatoires que si le protocole les retient.

EXEMPLE / UN RAPPORT PORTE SUR L’ANCIEN CODE

02

03

Le contrôle de A revient avec PASS.

!

RAPPORT PÉRIMÉ → ACCEPTATION REFUSÉE → TEST DE RÉGRESSION
TLA+ / TLC

Vérifier les invariants d’un modèle d’états.

TLC explore les transitions du modèle TLA+ dans un périmètre fini. Par exemple : une acceptation ne peut utiliser un rapport périmé. Une violation produit la séquence d’actions à l’origine du défaut.

fast-check

Rejouer les séquences sur le code TypeScript.

Les traces du modèle deviennent des tests du noyau pi-495. fast-check génère aussi des séquences d’actions et conserve les données nécessaires pour reproduire un échec.

Lean

Démontrer une propriété ciblée du noyau.

Lean peut démontrer une propriété de la combinaison des verdicts, sous des hypothèses explicites. Des tests de correspondance comparent ensuite le comportement TypeScript à cette référence.

Une exploration TLA+ vérifie le modèle déclaré ; une preuve Lean vérifie la propriété formulée. Les tests de correspondance avec TypeScript complètent ces résultats sans démontrer l’absence de bugs dans toute l’application.

10 / COMPRENDRE LES GARANTIES DU PROCESSUSPÉRIMÈTRE · VÉRIFICATION · ACCEPTATION

Ce qui est vérifié.
Ce que vous décidez.

Qu’est-ce qu’un harnais d’agents de code ?+

Un harnais organise l’exécution des agents : instructions, outils, permissions et sessions. pi-495 y ajoute un cycle de développement : spécifications, tests qualifiés, conception, implémentation, contrôles, revue et intégration Git.

Pourquoi un fichier d’instructions ne suffit-il pas ?+

Une consigne peut demander de préserver une API ou de respecter une dépendance entre modules. Il faut aussi vérifier ces propriétés. pi-495 associe les instructions à des tests, des contrôles structurels et des revues dont les résultats conditionnent l’acceptation.

Faut-il utiliser TLA+ et Lean pour chaque changement ?+

Non. TLA+ et Lean apportent des contrôles formels optionnels pour les invariants et interactions qui le justifient. Un changement courant peut être vérifié par des tests unitaires ou d’intégration, des contrôles de qualité et une revue de code.

Que signifie « accepté » ?+

La version du code proposée satisfait les vérifications obligatoires, les revues requises et les décisions humaines prévues par le protocole. Un contrôle absent, un rapport périmé ou une erreur d’outil ne compte pas comme une réussite. Le rapport précise ce qui reste non vérifié.

Que se passe-t-il si l’agent n’y arrive pas ?+

L’agent reçoit les contrôles en échec et les écarts à corriger, dans la limite des tentatives autorisées. Si le code ne progresse plus, si une capacité manque ou si une décision est nécessaire, pi-495 conserve l’état et indique comment reprendre.

Comment se passe l’intégration dans mon dépôt ?+

L’intégration locale est désactivée par défaut. Une fois autorisée dans la configuration et le candidat accepté, /495 integrate applique le changement au dépôt local et vérifie que l’arbre intégré correspond au code contrôlé. La publication distante et le déploiement relèvent de votre chaîne de livraison.
